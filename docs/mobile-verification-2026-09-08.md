Дата: 8 сентября 2026. Время в отчёте московское, если явно не указан UTC.

## Итог

Исправлен найденный при проверке дефект офлайн-режима PWA. Проверены приглашения и состав пати, восстановление сети, вход Steam и сохранение сессии Android.

Реальный вход Steam выполнен пользователем; пользователь отдельно подтвердил Steam Guard. Серверная запись успешного входа и сохранение сессии проверены инструментально. Физический iPhone не проверен: доступ к нему в этой сессии не предоставлен. Эмуляцию WebKit нельзя считать такой проверкой.

## Найденный Дефект И Исправление

Первый новый тест обнаружил реальную проблему: Service Worker сохранял `/offline` как Next.js-страницу, но не сохранял её стили и скрипты. Без сети она отображалась без оформления. Фоновое изображение перекрывало кнопку «Повторить».

Исправлено:

- Добавлен `public/offline.html`: автономный документ без Next.js, внешних стилей, скриптов и пользовательских данных.
- Логотип берётся из локального кеша, а не из сети.
- «Повторить» открывает исходный адрес, включая параметры приглашения. «На главную» ведёт в `/home`.
- Версия кеша обновлена до `aegis-arena-shell-v2`; удаляются только старые кеши приложения.
- API, авторизация, чужие домены и изменяющие запросы не кешируются этим обработчиком.
- В тестах проверяется не только видимость кнопки, но и настоящее нажатие с восстановлением страницы.

Первоначальное падение на Chromium воспроизведено и исправлено. Последующий сбой проверки из-за двух одноимённых заголовков исправлен в селекторе теста. Финальный прогон имеет 13 PASS и 2 SKIP, без упавших тестов.

## Сборки И Границы

До паузы нативные сценарии выполнялись на APK SHA-256 `A43C22CFBDE806F5429E369B50B62E9E167B815B296D6CF6A3EA54341C4FA3F2`.

За время паузы изменились Android-код и APK. На диске и в установленном приложении теперь совпадает SHA-256:

`6B7CEC95056C527D5DE2909EB1F86BC440285E67D705A6225BCE2E94B0F79F07`

В этой текущей сборке проверены действующая авторизация, серверная запись входа и сохранение сессии. Повторный запуск сценария с тестовыми аккаунтами намеренно остановился: APK уже был авторизован настоящим пользователем. Его сессия не удалялась и не заменялась тестовой.

Фактический Android API эмулятора по ADB: **37**. Это не физический Android и не iPhone. Debug APK использует адрес `10.0.2.2:3002`, предназначенный для Android Emulator.

Во время завершающей проверки параллельно обновились зависимости проекта до Next.js 16.3.4. Сначала команда сборки попала в момент обновления исполняемых файлов, затем обнаружила другой запущенный `next build`. Эти изменения и процесс не отменялись. Статус повторной сборки после освобождения блокировки фиксируется отдельно ниже.

Повторная production-сборка после освобождения блокировки: **PASS**, код завершения 0. Для host-запуска только на время команды заданы адреса PostgreSQL `localhost:5434` и Redis `localhost:6381`; `.env` не менялся. Есть предупреждения о старой секции `eslint` в конфигурации Next.js, переименовании `middleware` в `proxy` и слишком широком файловом трассировании в `server/storage/appearance.ts`. Их нужно разобрать в рамках обновления Next.js перед выпуском.

Браузерные результаты относятся к работающему стенду `localhost:3002` на момент прогона до обновления зависимостей. Они не заменяют отдельный E2E-прогон production-сервера новой версии Next.js.

## Повторный Запуск

```powershell
npm.cmd run check
$env:AEGIS_E2E_PARTY = '1'
npx.cmd playwright test tests/e2e/party-flow.spec.ts tests/e2e/pwa-recovery.spec.ts --project=iphone-webkit --project=iphone-chromium --project=android-small --output=test-results-mobile-report
```

Для APK нужен отладочный WebView, перенаправленный ADB на `127.0.0.1:9223`. Сценарии с временными аккаунтами запускаются только в вышедшем из аккаунта тестовом приложении:

```powershell
node scripts/verify-android-party.mjs
node scripts/verify-android-auth.mjs
```

Реальный Steam проверяется без подмены сессии:

```powershell
node scripts/verify-android-manual-auth.mjs prepare
# Пользователь самостоятельно завершает вход в Steam.
node scripts/verify-android-manual-auth.mjs verify
```

`verify` проверяет адрес возврата, серверную запись callback после начала проверки и сохранение сессии. Это подготовленный сценарий для следующего сквозного прогона; в текущем прогоне применён режим `session --guard-confirmed` после явного подтверждения пользователя. Возврат именно к приглашению после реального Guard в этом режиме не наблюдался; он покрыт отдельными автоматическими тестами.

## Что Осталось На iPhone

1. Предоставить доступный iPhone HTTPS-адрес стенда. LAN-адрес по HTTP подходит не для полной проверки Service Worker: ему требуется защищённый контекст. [Требование HTTPS](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).
2. В Safari открыть приглашение, пройти Steam/Guard вручную и проверить возвращение к тому же приглашению.
3. Добавить сайт на домашний экран и повторить вход из установленного приложения. [Инструкция Apple](https://support.apple.com/en-euro/guide/iphone/iphea86e5236/ios).
4. Проверить клавиатуру поиска, поворот экрана, системные отступы, копирование и системное меню «Поделиться».
5. Принять приглашение со второго аккаунта, увидеть изменение состава; проверить исключение лидером и отозванную ссылку.
6. Отключить сеть: экран должен сохранить оформление. Вернуть сеть и нажать «Повторить»; должен открыться исходный адрес.
7. Закрыть и заново открыть приложение; проверить сохранение входа. Зафиксировать модель iPhone, версию iOS и скриншоты без кодов, паролей и токенов.
